Making git safer

Signatures as a way to avoid spoofing attacks

by Francesco Agnoletto

Who wrote that code?

Git allows a developer to set a name and email. These are just config settings, and any value can be used as input.


              $ git config user.name "Timeea Saratean"
              $ git config user.email "tsaratean@opentext.com"
              $ git commit -m "Critical security patch (not really)"

This commit can be pushed to GitLab, and it will show the name and avatar of the account registered for that email.

There is no way to spot this as a fake.

This is a real vulnerability that can be used to:

  • Inject malicious code under a trusted name.
  • Create confusion between colleagues.
  • Target developers for bad conduct and security investigations.

The cryptographic signature

Commits can be signed cryptographically on git itself. The signature confirms the commits can only be created by the person who holds the private key and its password.

This is different than the standard SSh auth used by GitLab and GitHub.

How it works
  • Generate a public/private key pair.
  • Store the private key on your machine.
  • Upload your public key on GitLab.
  • When you commit, Git uses your private key to sign the commit's hash.
  • When you push, GitLab uses your private key to verify the signature.

the "Verified" badge

This is the badge GitLab displays for signed commits.

This badge confirms GitLab has cryptographically confirmed the author's commit identity.

Benefits

Authenticity

Signed commits can't be spoofed. Your identity is protected from external attackers or malicious insiders.

Accountability

There is no ambiguity for code authorship. Signed commits cannot be altered without losing their original signature.

Integrity

Being able to prove our code is exactly what our developers intended is a fundamental sign of trust.

Security compliance

For security audits like SOC 2 or ISO 27001, signed commits are a requirement and a huge plus.
